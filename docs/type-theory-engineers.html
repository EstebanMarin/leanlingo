Intuitionistic type theory, as seen from a compiler

Type Theory for Engineers

One rule runs everything in Lean: a type is a spec, a value of that type is an implementation, and the type checker decides if it fits. Proofs are just another kind of value.

The big picture

Three views of one thing

flowchart LR
  L["Logic
a statement P"] <--> T["Types
a type P"]
  T <--> C["Programs
a value h : P"]
  C <--> L
  T -.-> K{"Type checker:
does h have type P?"}
  K -- yes --> OK["P is proven ✓"]
  K -- no --> ER["compile error ✗"]

This is the Curry–Howard correspondence. Writing a proof and writing a well-typed program are the same activity.

How Lean checks your file

  


flowchart TD
  SRC["Your .lean file
def, theorem, by simp"] --> P["Parser"]
  IMP["import Mathlib
prebuilt .olean files"] --> E
  P --> E["Elaborator
fills in implicit args, _, type classes
runs tactics like simp, decide"]
  E --> CORE["Core term
tiny language: λ, Π, Σ via inductives,
application, universes"]
  CORE --> KER{"Kernel
small trusted type checker"}
  KER -- accepted --> OUT[".olean
reusable by other files"]
  KER -- rejected --> ERR["error in your editor"]


  

  
Tactics are code generators: by simp writes a proof term for you. The elaborator is big and clever; the kernel is small, and it re-checks every term, so a bug in a tactic can't sneak a false proof through.

Type : Type would allow a paradox, like a set containing itself. So every rung gets its own level. That's what universe u v in your code is about: write it once, work on every rung.






  
Σ is a tagged union

  
You've written dependent pairs before

  

    
TypeScript


type Answer =
  | { tag: true;  value: number }
  | { tag: false; value: string }

// the tag decides the value's type

    

    
Lean


def Answer : Bool → Type
  | true  => Nat
  | false => String

-- same idea, as a Σ type
#check (b : Bool) × Answer b

    

  

  
TypeScript hand-lists every case. Lean computes the second type from the first value, so it works for infinitely many cases, like (n : Nat) × Vector Nat n.






  
Tests vs proofs

  
A test checks some inputs. A proof checks all.

  

    
Unit test


test("add is commutative", () => {
  expect(add(2, 3)).toBe(add(3, 2))
  expect(add(0, 7)).toBe(add(7, 0))
})
// 2 inputs checked, infinitely many left

    

    
Theorem


theorem comm (a b : Nat) :
    a + b = b + a :=
  Nat.add_comm a b
-- every a, every b. Checked at compile time.
